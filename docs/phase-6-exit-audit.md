### 2.4 QA-02 redesign (documented deviation)

The plan's literal QA-02 compares `sum(line_total_cents)` to `orders.total_cents`. In the
shipped (and M1-verified) snapshot **every** order breaks that equality — stored line
totals are the seeded DQ-01 defect class and shipping/tax are legitimate parts of the
total — so the comparison cannot be the intended signal. The shipped exercise derives
`expected_total_cents = subtotal_cents + shipping_cents + tax_cents` and filters on its
mismatch with `total_cents`, surfacing exactly the six seeded DQ-02 rows (non-round
deltas). DQ-01 remains covered by `sql-adv-aggcorrect-12` (8 rows). The QA scenario
framing ("reconcile order totals against item totals") is unchanged; the reconciliation
chain is taught through the honest identity. Recorded in the plan as a deviation (§17 of
the plan amendments).

## 4. Server-side evaluation

`POST /api/v1/sql/evaluate` — result-envelope comparison, never SQL:

- Accepts `{ exerciseId, columns, rows, truncated? }` only; learner SQL is **never**
  sent to the server and never executed server-side; D1 carries control-plane rows only.
- Column-name match case-insensitive (no unexpected columns); rows compared as
  multisets by default or in order when the exercise demands it; integer-exact cents;
  NULL never equals empty string; `collate: nocase` where declared; numeric tolerance
  where declared; `truncated` envelopes can never pass; O(n log n) comparison.
- Request validation: 1 MB cap for this route only (existing 32 KB global guard intact),
  ≤1,000 rows, ≤64 columns, 10 KB cells, unique column names, no NaN/Infinity; malformed
  → 400; oversize → 413; unknown id → 404; no session → 401; 429 scoped rate limit
  (`sql-eval:<iphash>` 30/min).
- Pass threshold **70**; per-exercise rubrics (default `columns 30 + rows 70`,
  ordered `30/60/10`; `allOrNothing` for the rollback/integrity checks).
- Feedback is specific (counts, missing/unexpected columns, first mismatching cell
  position, ordering requirement) — no lorem.
- On a pass the caller's attempt is stamped `submitted` with the running-max best score
  (same atomic single-statement path as reports); on a fail the attempt stays
  `in_progress`. A fresh guest checking work on any exercise page gets an attempt row
  minted end-to-end (exercise start mints a clean guest session — see deviations).
- Reference solutions and expected rows are server-only compiled code; leak-linted.
- Exercise reveal (gated) ships the reference solution; Phase 3/4 reveals byte-compatible.

## 7. Security & data-leak review

- SQL execution stays in the browser worker (unchanged M1 client/worker; `deltaSql?`
  extension is additive; `reset` recreation reclaims memory).
- Learner SQL never reaches the server; no SQL-evaluation or execution route exists for
  it; D1 stores only attempts/reports/hint masks.
- Reference solutions, expected rows, corruption deltas, hint and reveal content are
  server-only modules (`sqlExercises.ts`, `sqlHints.ts`, `sqlReveals.ts`,
  `sqlSeedDelta.ts`, `sqlEvaluate.ts`) — never imported client-side; import-boundary
  and literal-content leak lint (`tests/lib/sql-leak.test.ts`, 33 checks) + post-build
  scan: zero corruption literals, zero expected figures, zero server-only module names
  in `dist/`.
- Hunt corruption activates only post-start and only for the SQL hunt in bug-hunt
  mode (403/404 matrix tested at HTTP level; deltas absent from clean sessions).
- Clean Mode cannot inherit bug-hunt corruption: clean sessions/exercises never fetch
  a delta; `PRAGMA foreign_keys=ON` for learners; the corruption deltas carry their own
  FK handling.
- Reset semantics: canonical reseed (+ active delta) on every Reset; worker recreation
  reclaims memory; reset restores the *exercise baseline* for exercises and the
  *corrupted* baseline for hunts.
- Request validation and limits: 1 MB evaluate cap; 30/min scoped budgets
  (evaluate/seed); global backstop; unknown ids indistinguishable (404); seed endpoint
  indistinguishable outside bug-hunt mode.
- Guest vs account privacy: attempts cascade with session TTL; customer binding only at
  submission time; no cross-customer read path; progress rows ownership-scoped; SQL ids
  are equally scoped (tests/server/sql-learning.test.ts).
- Phase 5 authentication and API behavior intact: `npm run check` green, including all
  API token, catalogue, cart, checkout, inventory, auth, hints, reveals, attempts,
  report-quality and maintenance suites (1106/1106).
- OpenAPI contract extended additively (38 operations, `/api/v1/sql/*`; 2 new error
  codes; version 1.0.0 → 1.1.0); leak lint, ref integrity and curated-route tests
  pass; `/api-reference` renders the new operations from the served spec.

## 10. Known limitations

  (3.54.1). If sql.js upgrades SQLite, `sql-adv-explain-04`'s expected spec must be
  regenerated (the 36/36 reference test will fail loudly).
- Answers remain visible to determined readers via devtools network inspection
  (accepted and documented in the plan §14).
- `/progress` Database Testing rows carry no "link to catalogue scenario" for exercises
  (exercises have no scenario page by design) — rendered as plain text with the exercise
  deep link instead.
- Guest progress expires with the practice session (7 days), as with the rest of the lab.
- Exercise attempt history is surfaced as the attempt-status chip on the exercise page;
  the full history view stays on `/practice` (unchanged Phase 4 surface).
- No OPFS persistence; every visit starts from the canonical snapshot.
- `wrangler pages dev` process management in local verification needs setsid/nohup;
  backgrounding from one-shot shells can reap it (observed once during this phase).
